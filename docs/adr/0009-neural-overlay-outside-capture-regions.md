# ADR 0009: Render the Neural Overlay Outside the Vision Capture Regions

## Status
Accepted

## Context
The connectome's internal state is invisible during a run. Every observable signal, meaning LPLC2 spike counts, Giant Fiber firings, CPG drive, GABAergic inhibition and gaze side, exists only in `SensoryState` and in the telemetry file written after the session ends, so a run can only be judged in hindsight.

A live panel is the obvious fix, but the screen is a shared resource with two systems that already own parts of it. `vision.py` grabs absolute screen coordinates through `mss`, so any window drawn over `VISION_CALIBRATION`'s eye boxes or `CAMERA_DETECTION`'s tablet patch is captured as if it were game content and corrupts the MSE comparison against the calibrated references. This failure mode is not hypothetical: a session on 2026-09-16 wrote `panic_left.png`/`panic_right.png` containing a screenshot of an unrelated application that had been left covering the capture area, and the fly reacted to that instead of the hallway. Separately, `input_controller.py` clicks absolute coordinates for the door and light buttons, so a window over those coordinates intercepts the click and the door never closes.

On the current 1920x1080 layout the game occupies roughly the top-left 1280x720. The only region inside the game frame that clears all three capture boxes is the strip from x=1018 to x=1280, which is exactly where the right door and light buttons live.

## Decision
The panel itself is a WebGL point cloud of all 138,639 somata, served by a stdlib asyncio HTTP server on loopback. `soma_coordinates_783.csv` is row-aligned with `2025_Completeness_783.csv`, so a connectome index maps to a point without any join, and `super_class` from the FlyWire annotations colours each point by region. Spiking indices are pushed as Server-Sent Events at the engine's own frame rate; the page holds a per-point intensity that is set on spike and decays every animation frame, which keeps a 10 Hz simulation legible at 60 Hz display without inventing data between frames.

The player runs the game fullscreen, so a window beside it is invisible. Rather than move the panel off-screen, `ingame_overlay_rect()` (`src/env/overlay.py`) looks for room inside the game frame itself: the two eye capture boxes leave a gap between them (`x` from the left box's right edge to the right box's left edge), and above `y=200` the camera-detection patch hasn't started yet, so the rectangle spanning that gap down to the patch's top edge is clear of every capture region and every motor click target at once. On the current layout that is a ~203x200 pocket at the top-center of the frame, derived from the same `VISION_CALIBRATION`/`CAMERA_DETECTION`/`MOTOR_CALIBRATION` values as `capture_regions()`/`motor_regions()`, verified against them with `rects_overlap()` before use, and never hardcoded, so a recalibration shrinks or removes the slot instead of silently drifting the panel over a capture region.

When that slot fits the configured `ingame_width`/`ingame_height`, the page loads with `?mini=1`, which hides the header, region bars and counters and leaves the point cloud, a one-line colour legend along the bottom and three corner dots for the two Giant Fiber lamps and the camera state, sized for a ~180x180 window instead of a 620x1040 one. Everything added to that page is absolutely positioned over the canvas, never in the layout flow, because anything in the flow would shrink `#stage`, resize the canvas and make `resize()` re-derive the camera distance, silently reframing the point cloud. If the slot doesn't fit, `_launch_brain_view_window()` falls back to the full side panel from `pick_overlay_position()`.

Getting that window on screen took three corrections, each of which failed silently:

- The browser was launched by bare name under `shell=True`. Neither `msedge` nor `chrome` is on PATH on a stock Windows install, and under a shell that failure arrives as an exit code, not an `OSError`, so the `except OSError` branch never ran, the function reported success, and no window ever existed. `find_browser()` now resolves a real path from the `App Paths` registry key with a fallback to the standard install locations, and the launch runs without a shell.
- The launch was handed to the browser the operator already had open, which exits immediately and ignores every window flag. The panel now runs under its own `--user-data-dir`, which also keeps it out of their signed-in session.
- `SetWindowPos` was called with `HWND_TOPMOST` as a bare Python `-1`. `HWND` is pointer-sized, so the value was truncated and the z-order request was dropped while the move and resize still appeared to work, so the window landed in the right place and stayed behind the game. It is now passed as a real `wintypes.HWND` with declared `argtypes`.

A fourth correction followed on 2026-09-17, from a run that logged `brain view window never appeared (browser exit code None)`. `None` is what `Popen.poll()` returns for a process that is still alive, so the browser was running and the panel was about to appear; the eight-second deadline simply expired first. A cold browser start, opening the profile directory and a page that fetches its WebGL library from a CDN all land inside that window, and a measurement on the same machine put the window on screen at 4.2 seconds, which is inside eight but not by much. The wait is now 45 seconds, and the window is located with `EnumWindows` and a substring match rather than `FindWindowW` and an exact one, because a browser is named after the URL until its document parses and only then adopts the page title. The two failures are also reported separately now: no window at all, versus a window that would not stay where it was put. The old code printed the same sentence for both.

Pinning once is not enough either. Going fullscreen makes the game itself topmost, which places it in front of anything pinned before it, and alt-tabbing re-orders the whole stack, so a panel pinned at startup is reliably on top only until the operator first clicks back into the game, which is immediately. A supervisor thread re-applies the placement every two seconds for the length of the night; the cost is two cheap calls, and it is how overlays over fullscreen games normally work.

`pin_as_overlay()` strips `WS_CAPTION` and `WS_THICKFRAME` so the panel reads as part of the game rather than as an application parked on top of it, adds `WS_EX_TRANSPARENT` so it can never intercept a click, and re-applies the whole thing until `GetWindowRect` confirms it, because the browser keeps laying its own window out for a second after it first appears and will undo a single move.

## Consequences
- The panel is visible during real fullscreen play, sitting inside the game frame in a pocket verified empty rather than beside a window the fullscreen game now covers.
- This depends on the game running borderless-style fullscreen, which is how a 2D Clickteam Fusion title typically implements it. A true DirectX-exclusive fullscreen would occlude any external window regardless of `WS_EX_TOPMOST`; there is no fix for that from outside the game process, only the side-panel fallback, which needs windowed or borderless mode to be seen at all.
- Windowed mode is not a workaround for that case: `vision.py` grabs `mss` screenshots at the absolute screen coordinates in `VISION_CALIBRATION`/`CAMERA_DETECTION`, and `input_controller.py` clicks the absolute coordinates in `MOTOR_CALIBRATION`. Both assume the game sits at the position it was calibrated at; moving to windowed shifts that position by the window chrome and invalidates every one of those coordinates at once.
- Panel geometry is derived at startup from the same config the capture and motor logic reads, so recalibrating `VISION_CALIBRATION` or changing resolution relocates or removes the pocket instead of silently poisoning the vision input.
- The panel reads the spike tensor and `SensoryState` only. It never writes, so it cannot perturb the simulation it is displaying.
- The server is stdlib asyncio and the page pulls Three.js from a CDN, so nothing is added to `pyproject.toml`. The page is read from disk per request, so its visuals can be iterated without restarting a night. `make_topmost_clickthrough()` uses `ctypes` only, for the same reason.
- A failed placement or a failed bind degrades to no panel, never to a corrupted run.
- The browser window steals focus once when it opens. It is launched during the warm-up countdown, which already exists so the operator can click back into the game before calibration starts.
